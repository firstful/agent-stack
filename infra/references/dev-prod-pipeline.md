# Dev/Prod Pipeline

Two independent agent-stack instances on separate machines, sharing a single git
monorepo. Per-environment configuration (hostnames, env vars, secrets) is
managed by Terraform, not by branching.

## Architecture

```
Dev machine (this host)                  Prod machine (remote host)
─────────────────────────                ──────────────────────────
Controller  ───  podman                  Controller  ───  podman
    │                                        │
cloudflared (dev tunnel)                  cloudflared (prod tunnel)
    │                                        │
*.dev.ffilt.us  →  slot-proxy             *.ffilt.us  →  slot-proxy
                        │                                       │
              fuse, engramic, ...                       fuse, engramic, ...
              (dev data / dev vault)              (prod data / prod vault)
```

Key properties:

| Aspect | Dev | Prod |
|--------|-----|------|
| Config source | Terraform workspace `dev` | Terraform workspace `prod` |
| Hostnames | `*.dev.ffilt.us` | `*.ffilt.us` |
| Tunnel | Separate dev tunnel ID | Existing prod tunnel ID |
| Vault | Dev vault (dev credentials) | Prod vault (real credentials) |
| Data volumes | Independent dev data | Independent prod data |
| Port range | 4000–4999 (local host) | 4000–4999 (different host) |
| Public exposure | Yes (dev tunnel) | Yes (prod tunnel) |

The two controllers are **fully independent** — each writes its own
`/tmp/stack.*.chash` markers, its own `runtime/services.json`, and manages its
own podman containers and networks. Config is applied per environment via
Terraform workspaces or variable files.

## Configuration Strategy

Per-environment configuration is managed by Terraform, not by git branches.
There is a single long-lived branch (`main`). The environment difference is
handled by Terraform workspaces or variable files.

### Directory structure

```
repos/<service>/
├── agent-stack.json            # Service definition (port, image, build, volumes, sidecars)
├── terraform/
│   ├── main.tf                 # Calls central module with per-service inputs
│   └── env/
│       ├── dev.tfvars          # Dev environment values
│       └── prod.tfvars         # Prod environment values
├── env-overlay.json            # Terraform output — checked in, consumed by controller

terraform-modules/               # Central Terraform module (separate git repo)
└── service-config/
    ├── main.tf
    ├── variables.tf
    └── outputs.tf
```

`agent-stack.json` owns the **service definition** — port, container image,
build arguments, volumes, sidecar declarations. It does NOT contain
environment-specific values (no `SECRETS.KEY`, no domain names).

Environment-specific config lives in Terraform, per service, and produces
an `env-overlay.json` that the controller merges at reconcile time.

### How it works

Each service repo has a `terraform/` directory that calls the central module:

```hcl
// repos/fuse/terraform/main.tf
module "config" {
  source = "git::https://github.com/ffilt/terraform-modules//service-config"

  service_name   = "fuse"
  domain_suffix  = var.domain_suffix

  env = {
    FUSE_DOMAIN  = "fuse.${var.domain_suffix}"
    DATABASE_URL = "postgresql://fuselocal:***@fuse--db:5432/fuse"
  }

  secrets = ["SESSION_SECRET", "JWT_SECRET"]

  expose_hostname = "fuse.${var.domain_suffix}"
}

resource "local_file" "overlay" {
  content  = module.config.overlay_json
  filename = "${path.module}/../env-overlay.json"
}
```

Per-environment variable files define only what differs:

```hcl
// repos/fuse/terraform/env/dev.tfvars
domain_suffix = "dev.ffilt.us"
```

```hcl
// repos/fuse/terraform/env/prod.tfvars
domain_suffix = "ffilt.us"
```

The central module (`terraform-modules/service-config/`) produces the
environment overlay as a JSON output:

```json
// repos/fuse/env-overlay.json  (generated by terraform, committed)
{
  "env": {
    "FUSE_DOMAIN": "fuse.dev.ffilt.us",
    "DATABASE_URL": "postgresql://fuselocal:***@fuse--db:5432/fuse"
  },
  "secrets": ["SESSION_SECRET", "JWT_SECRET"],
  "expose": {
    "hostname": "fuse.dev.ffilt.us"
  }
}
```

The controller loads both files at reconcile time:

```
loadDesired() reads each service's agent-stack.json
  → checks for sibling env-overlay.json
    → merges overlay.env into service.container.env
    → overlays expose config
    → secrets references are passed through to the vault resolver
```

### Applying

```bash
# Apply dev config for a single service
cd repos/fuse/terraform
terraform apply --var-file=env/dev.tfvars
# Writes repos/fuse/env-overlay.json

# Commit and push
cd ../..
git add fuse/terraform/ fuse/env-overlay.json
git commit -m "config: update FUSE_DOMAIN for dev"
git push
# → Controller detects commit within 5s via git-ref-watch
# → Reconcile reads the new env-overlay.json, restarts container
```

### What Terraform does NOT manage

Same as before — Terraform only writes the environment overlay. Everything
else is the controller's responsibility:

| Concern | Handled by | Why |
|---------|-----------|-----|
| Source code changes | Controller (git-ref-watch) | Terraform only writes env-overlay.json |
| Container images | Controller (podman build) | Builds from Containerfile + source |
| Blue-green swaps | Controller (reconcile.ts) | Zero-downtime slot swap logic |
| Health checks | Controller (waitForHealthy) | After each slot swap |
| Runtime state | Controller (writeRuntimeState) | Local to each machine |
| Cloudflare tunnel config | Controller (cloudflared.ts) | Generated from TUNNEL_ID/TUNNEL_DOMAIN env vars |

### Secret management

Secrets use the existing `{SECRETS.KEY}` pattern, resolved by the vault
adapter at deploy time (see #3 above). The `env-overlay.json` references
secrets via a `secrets` array that tells the controller which keys to
fetch. These are merged with any `{SECRETS.KEY}` interpolation patterns
in the env values.

Low-sensitivity env vars (hostnames, domain suffixes) are rendered directly
into `env-overlay.json` by Terraform. Credentials always go through the
`{SECRETS.KEY}` mechanism — never committed to git even in terraform files.

## Hostname Scheme

- **Dev**: `<service>.dev.ffilt.us` — e.g. `fuse.dev.ffilt.us`, `engramic.dev.ffilt.us`
- **Prod**: `<service>.ffilt.us` — e.g. `fuse.ffilt.us`, `engramic.ffilt.us`

Set via Terraform template variables in `infra/terraform/environments/*/terraform.tfvars`:

```hcl
# dev
domain_suffix = "dev.ffilt.us"

# prod
domain_suffix = "ffilt.us"
```

The template renders the hostname as `"${domain_prefix}<service>.${domain_suffix}"`.

## Tunnel Setup

Each machine has its own cloudflared tunnel credential.

### Controller code changes (already applied)

Two env vars were added to `infra/lib/cloudflared.ts`:

- `TUNNEL_ID` — Override the tunnel UUID (default: reads from
  `agent-stack.json` or `"agent"`)
- `TUNNEL_DOMAIN` — Override the wildcard ingress hostname (default:
  `"*.ffilt.us"`)

### Dev machine systemd unit

Add to `/etc/systemd/system/agent-stack.service`:

```ini
Environment=TUNNEL_ID=<dev-tunnel-uuid>
Environment=TUNNEL_DOMAIN=*.dev.ffilt.us
```

### Prod machine systemd unit

Either unchanged (defaults work) or explicitly:

```ini
Environment=TUNNEL_ID=ca308a1b-557a-4a18-9350-6eec27465bdf
Environment=TUNNEL_DOMAIN=*.ffilt.us
```

### Tunnel setup steps (one-time)

1. In Cloudflare Zero Trust dashboard, create a new tunnel for dev
2. Copy the tunnel UUID to the dev machine's systemd unit
3. Install cloudflared on the dev machine with the dev tunnel credential
4. Create DNS record: `*.dev.ffilt.us` → dev tunnel

## Promotion Workflow

```bash
# 1. Iterate on dev
# Edit source code in repos/<service>/ or update terraform/env/dev.tfvars
cd repos/fuse/terraform
terraform apply --var-file=env/dev.tfvars
cd ../..
git add fuse/terraform/ fuse/env-overlay.json
git commit -m "feat: add widget to fuse"
git push
# → Dev controller detects commit, builds, deploys on dev host

# 2. Test on dev
curl http://fuse.dev.ffilt.us/
# ... verify behaviour ...

# 3. Promote to prod
cd repos/fuse/terraform
terraform apply --var-file=env/prod.tfvars
# Then on the prod machine (or CI):
ssh prod-machine "cd /srv/agent-stack && git pull"
# → Prod controller detects commit, builds, deploys

# 4. Verify on prod
curl https://fuse.ffilt.us/
```

### What gets promoted

| Artifact | Mechanism | Cadence |
|----------|-----------|---------|
| Source code changes | `git push` → controller rebuilds on each machine | Every commit |
| Config/hostname changes | `terraform apply` with prod vars → committed overlay | On promotion |
| Secret rotation | Update Secret Manager → no deploy needed | Independent of code |
| Container images | Rebuilt from source by each controller | Per deployment |

## Unsolved Questions

### 1. Systemd services (appflowy, files) — RESOLVED

**Decision:** These stay on dev only. The prod machine runs only
container-based services. No systemd units, no Docker Compose, no Node.js file
server.

Services defined with `"service": { "type": "simple" }` (`appflowy`, `files`)
are excluded from the prod Terraform workspace — their templates either don't
exist or produce `agent-stack.json` with `"expose": { "enabled": false }`.

### 2. LLM endpoints and provider URLs — DEFERRED

**Decision:** Ignored for now. The `host.containers.internal:8080` references
stay as-is in both environments. On prod, those service features will simply
not function until a production LLM endpoint is wired in.

```json
"LLM_ENDPOINT": "http://host.containers.internal:8080/v1/chat/completions"
```

When prod needs LLM access, the endpoint will be updated in the prod
`terraform.tfvars` to point at whatever serves it (dedicated inference
container, remote API, etc.).

### 3. Vault — RESOLVED

Secrets are resolved via `{SECRETS.KEY}` → reading from a vault HTTP API.

**Decision:** Unified GCP Bridge service on Cloud Run. Single service
handles both vault (secret resolution) and monitoring (controller health
checking). Scale-to-zero, free tier.

Architecture:

```
gcp-bridge (Cloud Run, min-instances: 0)
├── /vault/api/secrets/plain/:service     — vault API (Secret Manager backing)
├── /monitor/check                        — monitoring poll endpoint (Cloud Scheduler trigger)
└── /monitor/config                       — returns configured target URLs
```

**Vault path** (`/vault/...`):
- Backed by GCP Secret Manager
- Environment awareness via `X-Environment` header (dev/prod)
- Secrets named `{env}-{service}-{KEY}` in Secret Manager
- Controller sets `VAULT_URL=https://gcp-bridge-xxxx.run.app/vault`
- Controller already passes `VAULT_TOKEN` as Bearer auth → bridge validates

**Monitor path** (`/monitor/check`):
- Triggered by Cloud Scheduler (every 5 minutes)
- Fetches `GET /api/status` from each configured controller URL
- Checks: `lastReconcile` timestamp is recent, `reconcileErrors` empty,
  `buildErrors` absent
- Logs metrics to Cloud Monitoring; alerts via notification channel
- Config: `MONITOR_TARGETS` env var (JSON map of env → controller URL)

Secret retrieval is already deferred to deployment time (see analysis in
reconcile trace above). The bridge stays at zero instances between deploys
and monitoring polls.

**Free tier:**

| Component | Usage | Free tier | Headroom |
|-----------|-------|----------|----------|
| GCP Bridge (Cloud Run) | ~8.7K req/mo | 2M req/mo | 230× |
| Secret Manager | ~5 secrets | 5 free | 1× (fine) |
| Cloud Scheduler | 1 job | 3 free | 3× |
| Cloud Monitoring | Minimal custom metrics | 10K writes/mo | plentiful |

Implementation plan:
1. Write Go gcp-bridge service (vault handler + monitor handler)
2. Create central `gcp-bridge` Terraform module (Cloud Run + IAM + Scheduler)
3. Each service's terraform/calls the vault module for env-overlay.json
4. One-line patch to the controller: pass `X-Environment` header in
   `fetchSecrets()` call
5. Set `VAULT_URL` on controllers to the bridge's vault sub-path
6. Remove local vault container from the desired set
7. Migrate existing secrets from local vault JSON to Secret Manager

### 4. Schema migrations during blue-green — RESOLVED

**Decision:** Expand-contract (additive-only) pattern.

Phase 1 — **Expand** (additive migrations): new columns, new tables, new
indexes only. Old code ignores them; new code uses them.

Phase 2 — **Swap**: blue-green slot swap via the controller's health check
gate. Migration runs as part of the container's startup entrypoint, before
the app serves traffic. The controller's `waitForHealthy()` call naturally
gates the swap — if the migration fails, the health check fails and the
new slot is rolled back.

Phase 3 — **Contract** (cleanup): remove deprecated schema elements after
a safe grace period (manual or scheduled job, not part of deploy).

Key rules:
- Additive-only migrations as a hard convention
- Migration runs in the container entrypoint (ORM auto-migrate or explicit
  script) — no separate migration-runner container
- Health check endpoint must be gated on migration success
- Contract phase is decoupled from deploys — run after confirming the old
  slot is gone and won't be rolled back
- No backward-incompatible changes during a deploy (no DROP, no RENAME,
  no NOT NULL on existing rows)

### 5. Data volume initialisation for prod — RESOLVED

**Decision:** Self-bootstrapping. Each service initialises itself on first
start.

Schema creation is handled by the entrypoint migration (see #4 above —
expand-contract pattern, runs at container startup). Default admin accounts
or initial reference data are created by a first-run check in the
application code (e.g. "if admin table is empty, seed default").

No copying from dev. Services that need non-trivial seed data (e.g.
taxonomies, templates) get a dedicated seed script that can be triggered
via an API endpoint or CLI, but the service must operate without it — the
seed adds data, the service doesn't require it to start.

Key rules:
- Every service must start and pass its health check with empty volumes
- Default credentials (if any) are set via `{SECRETS.KEY}` env vars, not
  hardcoded in the application
- Seed scripts are additive — safe to run multiple times on a running
  service

### 6. Config drift between environments — RESOLVED

**Decision:** Embedded check in the controller's reconcile loop.

The `reconcile()` function in `reconcile-worker.ts` already runs on every
git push and every heartbeat. A new step scans `infra/terraform/templates/`
for `{${var}}` patterns, then checks both
`environments/dev/terraform.tfvars` and `environments/prod/terraform.tfvars`
have the variable defined. Missing vars are reported as reconcile errors
alongside build failures — surfaced in the controller's status dashboard
and error output.

Graceful: if the `infra/terraform/` directory doesn't exist, the check is
skipped entirely (no error). This lets the controllers run without the
Terraform setup being present.

Implementation: a single function `checkTerraformVars()` added to
`reconcile-worker.ts`, called after loading the desired service set.

### 7. Terraform state management — RESOLVED

**Decision:** GCS backend, shared between machines.

Remote state in a GCS bucket (`gs://firstful-terraform-state/`). Each
environment uses a different prefix:

```hcl
terraform {
  backend "gcs" {
    bucket = "firstful-terraform-state"
    prefix = "env/${terraform.workspace}"
  }
}
```

Required because the vault adapter's Cloud Run service and IAM resources
are managed by Terraform in GCP. Local state would orphan those resources
if the dev machine failed.

| Concern | Mitigation |
|---------|------------|
| State contains sensitive values | Enable GCS bucket encryption (default) + object versioning for recovery |
| Concurrent applies | GCS backend uses object-based locking — safe per prefix |
| State portability | GCS is accessible from dev machine, prod machine, CI, laptop

### 8. Monitoring and alerting — RESOLVED

**Decision:** Handled by the GCP Bridge's `/monitor/` path (see #3 above).

Single Cloud Run service, single deployment — vault and monitoring share
the same binary, same scale-to-zero lifecycle. Cloud Scheduler triggers
the monitor check every 5 minutes.

Free tier covers it entirely (see #3 for numbers).

### 9. Rollback of data-breaking changes — RESOLVED

**Decision:** Podman volume snapshots before promotion.

Before a slot swap, the database volume is snapshotted:

```bash
podman volume export <service>--db-data | gzip > /backups/<service>-pre-$(date +%s).gz
```

Rollback procedure:
1. Stop the new slot (controller handles this on health check failure)
2. Restore the volume: `gunzip -c <snapshot> | podman volume import <service>--db-data -`
3. Restart the old slot

Snapshots are taken by the controller as part of the blue-green flow —
added to `ensureContainer()` before `runContainer()` for the idle slot.
Stored under `/var/lib/agent-stack/backups/` with a retention of 7 days
(cleaned up by the same reconcile loop).

The expand-contract migration strategy (#4) already prevents destructive
schema changes during deploys — this is an additional safety net for
unexpected data corruption or a bad migration in the expand phase.

### 10. Controller reconciliation vs Terraform file writes — RESOLVED

**Decision:** Moot — Terraform no longer writes controller config files.

Terraform writes `env-overlay.json` to the service's own repo directory.
This file is committed to git alongside the terraform sources. The
controller's git-ref-watch catches the commit within 5 seconds — same as
any source code change. There is no separate write path to reconcile.
